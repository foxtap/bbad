# 事故取证：`connect()` 被自己的静态方法吞掉（2026-09-15）

> 一句话：**一个 `@staticmethod` 插进了别人函数体的中间**，把 `connect()` 的后半段
> 整段变成死代码 —— 工具**一个连接都不建**，而 `compileall` 全过、`grep` 也看得出来
> 那些代码"还在"。发现于补日志守卫、跑 `tests/test_diag.py` 时。

---

## 1. 症状

跑 `tests.test_diag` 时，`TestConnectFailureLogging` 里 **5 条**用例报
`AssertionError: Exception not raised`；成功路径那条报 `'已连接' not found in …`。

日志抓到的输出只有两行（本该有十几行）：

```
INFO:ad_client:[op05] 连接开始 dc=192.0.2.9 port=389 ssl=False user=corp\admin（原写法）…
INFO:ad_client:[op05] RootDSE 反查成功（0.00s）host=dc01.corp.example.com domain=… 功能级别=7
```

—— 到此为止，没有"NTLM 绑定身份"、没有"已连接"。**`connect()` 在反查之后就返回了。**

## 2. 根因

为了修「域控连不上时给的方向反了」，往 `ad_client.py` 加了个静态方法
`_no_base_dn_message`。它的定义落在 `connect()` 的函数体中间：

```python
    def connect(self, cfg):
        ...
            raise AdToolError(self._no_base_dn_message(probe_failure), ...)

    @staticmethod                      # ← 4 格：这一行结束了 connect()
    def _no_base_dn_message(failure):
        """…"""
        if failure is not None:
            return failure.message
        return "无法自动反查 BaseDN。"

        # ↓↓↓ 以下全都是 connect() 原本的后半段，8 格
        from ldap3 import Connection, NTLM, Server     # 建连接
        conn = Connection(...)
        self._conn = conn
        ...
        _log.info("[%s] 已连接 …")
        return info
```

`_no_base_dn_message` 的两个 `return` 都在前面且无条件 ⇒ 后面那 16 条同级语句
**永远执行不到**。用 AST 量：

| 函数 | 直接语句数 | 末行 |
|---|---|---|
| `connect`（修前） | **14** | 444 |
| `_no_base_dn_message`（修前） | **19**（含 16 条死代码） | 558 |
| `connect`（修后） | 30 | 565 |

## 3. 为什么"看着没事"

| 检查 | 为什么抓不到 |
|---|---|
| `py_compile` / `compileall` | **语法完全正确** —— 死代码是合法 Python |
| `grep` 找 `Connection(` | 代码还在文件里，有引用、有调用，静态检查眼里是"活"的 |
| 通读 diff | 新加的静态方法**缩进看起来很正常**（4 格，与其它方法一样）—— 没人会去数它上面那句 `raise` 属于谁 |
| "跑一遍试试" | 出事的那段逻辑恰恰是**没被执行**的：桩替身把 `probe` 喂饱后，`connect()` 就悄悄返回了 |

## 4. 破坏面（实测，反证 C30/C31）

把事故原样注入回去，看有多少用例会红。**补测前 / 补测后**：

| 套件 | 用例总数 | 会红（补前） | 会红（补后） | 补的是哪些 |
|---|---|---|---|---|
| `tests.test_ad_client` | 156 → **166** | **4** | **12** | 新增 `TestConnectSuccessPath` 10 条（原 4 条：`test_manual_values_override_what_probing_found`、`test_probe_failure_falls_back_to_the_manually_typed_base_dn`、`test_bind_failure_appends_the_netbios_hint`、`test_bind_failure_with_a_domain_qualified_account_omits_the_hint`） |
| `tests.test_diag` | 51 → **52** | **5** | **5** | 连接日志那一组（`TestConnectFailureLogging`） |

**"整个连接功能失效"当时只让 9 条用例变红** —— 这才是最值得记下来的数字：
`connect()` 的**成功路径**几乎没人走到（绝大多数用例直接 `client._conn = conn`
摆好替身，见 `ClientTestCase._build`）。事故能溜过去，不是因为判据不够多，
而是因为**能红的本来就不多**。

⇒ 所以补了两样东西，缺一不可：

1. **与运行无关的静态判据**（`tests/test_source_hygiene.py`）—— 不依赖任何人去跑通 `connect`；
2. **真正走完 `connect()` 的 10 条用例**（`TestConnectSuccessPath`）——
   逐条钉住"连完之后必须发生的事"：持有活连接 / 连的是配的那台与端口 /
   身份归一成 `域\用户` / cfg 回填 / 改密链装配 / 审计归属 / 重连先断旧链 /
   断连真的 unbind。事故注入后这 10 条**全部变红**（C30 精确钉住）。

> 其中 `test_reconnect_clears_the_children_cache` **不在**红色清单里：
> `connect()` 开头调的 `disconnect()` 也会清那份缓存 ⇒ 拆掉 `connect` 里那句
> 仍然绿。这类"两处都保证了同一件事"的用例要如实说明它守的是哪一层，否则
> 看反证结果的人会以为判据漏了。

## 5. 修法

1. 把 `_no_base_dn_message` 挪回**类级别**（放在 `connect()` 前面），并在它的
   docstring 里写明「本方法必须留在类级别」，附上这次事故的形状。
2. 新增静态守卫 `tests/test_source_hygiene.py`：
   函数体里出现「**无条件 `return`/`raise` 之后还有同级语句**」即判违规。
   - 递归进 `if`/`try`/`with`/`for`/`while`/`match` 的**语句块**；
   - 不进**嵌套函数/类**（各自单独扫，否则同一处报两遍 = 噪音）；
   - 三头自检都做了：正例命中 / 正常控制流不误伤 / 嵌套函数恰好只报一次 /
     干净模块返回空集 / 语法错误要报出来而不是静默空集；
   - 附**扫描面自检**（文件数 ≥ 30 且必须含 `ad_client.py`）—— 没有它，
     清单哪天返回空集，这条守卫会**静默变绿**。
3. **补 10 条走完 `connect()` 的成功路径用例**（`TestConnectSuccessPath`），
   并把 `TestConnectFallback` 的私有夹具提成共享基类 `ConnectTestCase`
   （两半走的是同一个入口，夹具只该有一份）。
4. 反证 `tools/counterproof_hygiene.py`（把事故**原样注入**）：

| 组 | 注入 | 期望精确变红 |
|---|---|---|
| C29 | 静态方法插进 `connect` 体内 | 恰好 1 条：`test_no_function_hides_code_after_an_unconditional_exit` |
| C30 | 同上，跑 `test_ad_client` | 恰好 12 条（见上表） |
| C31 | 同上，跑 `test_diag` | 恰好 5 条（见上表） |

源码无论成败都还原，并核 md5。

## 6. 顺带修掉的三处

- **`describe_exception` 把同一个数印两遍**：`pywintypes.com_error` 的
  `args[0]` **就是**它的 `hresult`（实测 `exc.hresult == exc.args[0]`），
  所以 `hresult=0x800708C5 | errno=-2147022651 | …` —— 既重复又错名
  （那个数是负的，像坏数据）。现在有 `hresult` 属性时不再出 `errno=`。
- **测试里的十进制常量手算错位**：`0x800708C5` 应为 `-2147022651`，原写成
  `-2147023659`（= `0x800704D5`）—— 判据看着在验 hresult、其实验的是另一个错误码。
  ⇒ 常量别手算，写清算式。
- **`code=%s` 在两条通道上不对等**：`connect` 早先清掉了（没码时会打出
  `code=None` 这种噪声），`test_connection` 还留着 ⇒ **同一个缺陷只修了一半**。
  现在两条通道共用 `diag.describe_exception`（它只在**真有码**时才写
  `code=…`，有 `result` 字典时不重复写）。配两面判据
  `test_neither_channel_prints_a_blank_code`：没码 ⇒ 一个字都不写；
  有码 ⇒ 必须写出来（只验前半句的话，"把 code 整个删掉"也能过 —— 那是扔线索）。

## 7. 教训（可复用）

1. **"有引用、有调用"不等于"能被执行到"。** 静态检查的盲区正是"整段被吞"——
   而它偏偏是"功能全废"这种最严重的后果。
2. **编辑事故的形状是可以被静态判据精确刻画的**：这次是"`return` 之后的同级语句"。
   凡是"缩进决定归属"的语言，这个形状都会重演（把类方法插进函数体中间）。
3. **量破坏面。** "9 条会红"比"全绿"更有信息量：它告诉你哪条是真正的守卫、
   以及"为什么它能溜过去"。补完用例再量一次（9 → 17），补测才算**做完了**
   而不是"我觉得够了"。
4. **"跑得通"和"跑得到"是两件事**：这条事故的形状是"代码还在、只是永远执行不到"，
   任何**执行**层面的检查都看不见它（`compileall` 过了、`grep` 也看得见）。
   要抓它只能靠**静态的形状判据**（`return` 之后还有同级语句）或**覆盖率报告**。
5. **守卫要配扫描面自检。** 扫描面为空 ⇒ 判据恒真 ⇒ 静默假绿。这是本项目
   反复踩过的同一类坑（幽灵名单 / 硬编码套件清单 / 被 docstring 满足的判据）。

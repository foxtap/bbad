# 回归慢的根因：界面测试的窗口泄漏（2026-09-15）

> **结论先说**：`test_ui_smoke` 一个模块吃掉回归的大部分时间。根因不是"用例写得多"，
> 而是每个用例都在**泄漏一个没被销毁的主窗口** —— `close()` 只隐藏窗口，Qt 的
> top-level widget 列表会一直持有它（连带 4 个 `QMenu` 和 8 个 `QFrame`）。于是每个用例
> 要把越来越多的控件遍历一遍，**越跑越慢**。
> 修复后该模块：**≥630s（10.5 分钟只跑完 69/97 例）→ 62.2s（97 例全绿）**。

---

## 1. 定位过程（每一步都在排除一种猜测）

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① 按模块计时 | `tools/regression_timing.py` | `test_ui_smoke` **>240s 被标 TIMEOUT**；其余 23 个模块合计 **~100s**（次慢 `test_mock_client` 37.9s） |
| ② 怀疑 setUp/tearDown 固定开销 | 手写探针跑一遍 setUp→tearDown 并分段计时 | 合计仅 **0.131s**（`MainWindow()` 0.036 / `show()` 0.002 / `start()` 0.085 / `shutdown()` 0.000）⇒ **排除** |
| ③ 怀疑某些用例特别慢 | 单跑 1 例、单跑一个类 | `TestWindowStartup` 7 例 **1.32s**、`TestDemoBrowsing` 单例 **0.58s** ⇒ **单跑都很快**，排除 |
| ④ 逐例计时同一个类 | `TestResult` 子类记每例耗时 | **单调递增**：0.570 → 0.700 → 0.810 → … → **2.041s** |
| ⑤ 统计存活的 Qt 对象 | `QApplication.topLevelWidgets()` / `allWidgets()` | **每例 +13 个顶层窗口 / +396 个控件**：13→26→39→52→65… |
| ⑥ 解剖对象类型 | 按 `type(w).__name__` 计数 | `{'MainWindow': n, 'QMenu': 4n, 'QFrame': 8n}` |
| ⑦ 找引用者 | `gc.get_referrers()` | `QMenu` 被 `QMenuBar` 持有 ⇒ 主窗口不销毁，菜单与浮层跟着留下 |

**关键判据是 ④⑤**：单跑快、整套慢 ⇒ 几乎一定是**累积效应**；而对象计数把累积
变成了可观测的事实（不是"我觉得"）。

---

## 2. 根因

`UiSmokeCase.tearDown` 只调 `self.win.close()` —— **`close()` 是"隐藏"，不是"销毁"**。
Qt 的 top-level widget 列表会一直持有那个窗口，连带它的 4 个下拉菜单（`QMenu`）与
8 个浮层（`QFrame`）。而用例内部大量调用 `pump()` / `processEvents()` / `idle()`
（都在**转事件循环**）⇒ 每次转要遍历的控件越来越多 ⇒ 每例越来越慢。

所以"回归 15 分钟"不是产品代码变慢，是**测试自己在给自己加负载**。

---

## 3. 修法（有一个反直觉的坑）

```python
self.win.close()
self.win.deleteLater()
_app.sendPostedEvents(None, QEvent.Type.DeferredDelete)     # ← 关键
```

⚠️ **`QCoreApplication.processEvents()` 默认不处理 `DeferredDelete` 事件**（Qt 文档明说）。
所以「`deleteLater()` + `processEvents()`」这个看起来就是标准答案的组合**是无效的** ——
实测反而更糟（顶层窗口涨到 143 个、11 例 19.2s，比不清理的 14.5s 还慢）。
**必须显式把这批事件投递出去**。

---

## 4. 实测对比（同一个类，11 例）

| 清理方式 | 11 例耗时 | 顶层窗口 | 耗时曲线 |
|---|---|---|---|
| 不清理（原状） | 14.5s | 13→78（递增） | 单调递增 0.57→2.20s |
| `deleteLater + processEvents` | **19.2s** | 13→143 | 更差 |
| **`deleteLater + sendPostedEvents(DeferredDelete)`** | **6.6s** | **恒为 0** | **平坦** 0.40~0.75s |
| `setParent(None) + deleteLater + sendPosted` | 6.6s | 恒为 0 | 平坦（不比上面更好，故不采用） |

整个模块：**≥630s → 62.2s（`Ran 97 tests in 62.217s … OK`）**。

**全量回归（991 例）**：**`Ran 991 tests in 117.585s … OK`** —— 修复前同一个命令是 **539.8s**，
**降幅 78%**。回归终于回到"改一行、跑一遍"可接受的时间。

| | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| `test_ui_smoke` | ≥630s（10.5 分钟只跑完 69/97 例） | **62.2s** | ≈ 10× 快 |
| 全量 991 例 | **539.8s** | **117.6s** | **-78%** |

## 5. 五条可复用的教训

1. **「慢」要量，不要猜。** 我先怀疑 setUp 开销（0.131s，排除）、再怀疑个别用例
   （单跑很快，排除），最后靠**逐例计时 + 对象计数**才看见"越跑越慢"。
2. **单跑快、整套慢 ⇒ 几乎一定是累积效应**（泄漏 / 全局状态 / 缓存），不是"某个用例慢"。
3. **`close()` ≠ 销毁。** PyQt 里要真正释放必须 `deleteLater()`，而且
   **必须显式投递 `DeferredDelete`**。
4. **"看起来对的组合"也必须实测。** `deleteLater() + processEvents()` 是这类问题的
   通行答案，在这里就是无效的。判据要落在**可观测事实**（对象数降到 0）上，
   不是"代码看着对"。
5. **累积效应会让"绿"变得昂贵，而且长期没人察觉。** 97 例一直是绿的 —— 直到回归
   从 2 分钟涨到 15 分钟，让人误以为是产品代码变慢（本次就白查了一轮）。
   **回归耗时本身要当指标看。**

---

## 6. 与产品代码的关系

**产品代码没问题**：`MainWindow` 是应用唯一的主窗口，只创建一次；
`closeEvent` 里也确实收干净了工作线程（`runner.shutdown(wait_ms=4000)`）。
这是**测试夹具**的卫生问题（每例新建一个主窗口），修的是 `tests/test_ui_smoke.py`
的 `tearDown`，不动产品逻辑。

备份（改动前）：`%LOCALAPPDATA%\Temp\test_ui_smoke.py.bak-before-leakfix`

## 7. 补的判据：把"弱信号"换成"硬信号"（同日追加）

修好之后还留着一个隐患：**这个缺陷没有任何判据兜底**。它不会让用例变红，只会让
回归变慢 —— 而"耗时"是个**弱信号**：受机器负载影响、不好断言、还容易被误读成
"产品代码变慢"（本次就因此白查过一轮）。所以补了三层：

| 层 | 位置 | 判据 | 覆盖 |
|---|---|---|---|
| 断言 | `UiSmokeCase.tearDown` 末尾 | 拆完后 `topLevelWidgets()` **不得超过**进来时记下的数 | 全部 **98** 例（每条继承它的用例） |
| 判据自检 | `TestWindowLeakGuardSelfCheck` | 裸 `QWidget` 走「建 → `close` → 销毁」：**出现 / 仍在 / 消失** | 证明上面那条断言**有分辨率**，不是恒真空转 |
| 反证 | `tools/counterproof_ui_window_leak.py` | 打桩 `MainWindow.deleteLater` 为 no-op ⇒ 空白用例**精确红 1 条**；还原后全绿 | 证明上面那条断言**真的承重** |

三条判据一次跑完的开销可以忽略（自检 0.002s）。

### 三个设计决定，每个都是踩过才定下来的

1. **断言用"不超过"而不是"等于 0"**：整模块跑的时候，进程里本来就留着别的窗口的
   待删对象，`topLevelWidgets()` 不为 0 是常态。用绝对数会把**正确**的行为判成失败。
   相对判据（`after <= before`）既抓得住真泄漏（+13），也容得下旁人残留。
2. **判据自检用"对象身份"而不是"计数差值"**：`sendPostedEvents` 会**捎带**把别人的
   待删对象一起清掉 ⇒ 计数差值会失真（实测差值变成 `-2`，把一条**正确**的行为判成
   失败）。`widget in _app.topLevelWidgets()` 不受旁人影响。
3. **反证每段起独立子进程**：同进程里做过一版，结果是**假失败** —— 泄漏窗口的
   Python 引用挂在 `TestResult` 里的 test 对象上，result 一被回收，最后一个引用
   归零，PyQt 顺手就销毁了 C++ 对象 ⇒ 下一段的起点在 0 和 5 之间飘。
   进程级隔离之后每段起点必然干净。

### 数字的口径（两个都对，别混用）

| 时机 | 顶层窗口 | 控件 |
|---|---|---|
| `setUp` 刚结束（演示页还没建） | 5 | 65 |
| **一条用例跑完（`tearDown` 之前）** | **13** | **396** |

本文 §1⑤ 与 §2 说的"每例 13 个顶层窗口 / 396 个控件"是**后一个口径** ——
11 条用例逐条统计，**全部稳定在 13/396**（这也说明计数判据本身是稳的）。

### 补完判据后的实测

| | 例数 | 耗时 |
|---|---|---|
| `tests.test_ui_smoke` | **98**（原 97，+1 条判据自检） | **58.3s** |
| 全量 | **992**（界面 4 模块 141 + 后端 20 模块 851） | **112.5s**（`Ran 992 tests … OK`） |

反证 `tools/counterproof_ui_window_leak.py` 三段结论：基线绿 → 打桩后**精确红 1 条**
（`AssertionError: 5 not less than or equal to 0`）→ 还原后绿。

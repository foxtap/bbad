## 1. 一次连接在日志里长什么样

下面是一次**真实**的连接失败（本机连不上域控，09-15 实测原文，已脱敏）：

```
[op01] 连接开始 dc=192.0.2.10 port=389 ssl=False user=corp.example.com\zhangsan（原写法） 手填 domain=（留空→自动反查） base_dn=（留空→自动反查）
连接域控失败（网络层，一个字节都没连上）：LDAPSocketOpenError | raw=socket connection error while opening: timed out
探测失败 192.0.2.10:389：连不上（网络不可达 / 超时 / 防火墙拦截） ｜ LDAPSocketOpenError | raw=…timed out
探测失败 192.0.2.10:636 (SSL)：连不上（网络不可达 / 超时 / 防火墙拦截） ｜ LDAPSocketOpenError | raw=…timed out
[op01] RootDSE 反查失败（10.09s）AdToolError | raw=连不上 192.0.2.10（已尝试…）这不是账号或域名的问题…
[op01] 中止：反查不到 BaseDN 且未手填。端口可达性 389(LDAP)=TIMEOUT/1510ms 636(LDAPS)=TIMEOUT/1509ms 135(RPC-EPM)=TIMEOUT/1509ms 445(SMB)=TIMEOUT/1509ms 88(Kerberos)=TIMEOUT/1508ms ⇒ 389/636 都不通 → 先解决网络（域网络 / VPN / 防火墙），别去查账号
```

一次尝试里的每一行都带**同一个 `op01` 编号** —— 十几行日志夹着别的线程输出也不会看串。

启动时另有一条**环境快照**（排障前先看它）：

```
[启动] 环境 工具版本=1.0.0 运行形态=源码直跑 程序路径=… Python=3.13.14 操作系统=Windows 11 … 本机名=… 本机域状态=未加域（或读不到域环境变量） PyQt6=6.9.1 pyqtdarktheme-fork=2.1.0 ldap3=2.9.1 pycryptodome=3.21.0 pywin32=310 MD4=可用（pycryptodome）
```

`MD4=` 这一项是**只有真域才发现得了**的依赖（缺了它 NTLM 必然失败，而所有用替身的
测试都不会红 —— 假 ldap3 从不真算 NTLM）。

## 1.5 ⚠️ 同日事故：`connect()` 被自己的静态方法吞掉（已修 + 已配静态守卫）

修「方向反转」那个缺陷时加了个 `_no_base_dn_message`，**插错了位置**：
`@staticmethod` 那行缩进 4 格、落进了 `connect()` 的函数体中间 ⇒ `connect()` 的
后半段（建连接 / 装配改密链 / 审计 / 返回）**整段变成死代码**，`connect()`
探完 RootDSE 就返回 `None`，**一个连接都不建**，而 `compileall` 照样通过。

- 详细取证与教训：`docs/事故-函数体被吞-2026-09-15.md`
- 新增静态守卫：`tests/test_source_hygiene.py`（函数体里**无条件 `return`/`raise`
  之后还有同级语句**一律判违规，与运行无关、插错就成立）
- 反证：`tools/counterproof_hygiene.py`（C29~C31，把事故原样注入，精确变红）

## 1.6 ⚠️ 同日第二个缺陷：排障脚本自己**不初始化日志**（已修 + 已配守卫）

`diagnose_connect.py` 与 `verify_connect_wiring_live.py` 都**不初始化日志**
（"记日志是 `main.py` 的事"）⇒ 两个后果，第二个更坏：

1. 脚本自己产出的日志**一行都不落盘**。终端里看着有（WARNING 以上被 logging 的
   lastResort 打到 stderr），`app.log` 里一条没有 —— **09-15 实测：跑完脚本，
   日志最后一行还停在 `2026-09-14 17:43`**。
2. 脚本第 ⑥ 步打印的**是上一次 GUI 运行留下的旧日志**；而
   `verify_connect_wiring_live.py` 的**判决判据**正是「日志里有没有 `TypeError`」
   ⇒ 本次明明没报错、上一轮报过，它照样捞出**上一轮那条 TypeError** 并宣告
   「装配还是断的」。**判据读到陈旧数据，比没有判据更坏。**

修法（守住"只有一份实现"）：

| 改动 | 说明 |
|---|---|
| `utils.bootstrap_logging()` | 把 `main.py` 里那份初始化**提上来**，GUI 与所有 tools 脚本共用、写**同一个** `app.log`。函数体内才 `import config` —— `config.py` 顶部 `from utils import …`，模块级 import 会成环 |
| `utils.read_log_tail(path, lines=, needle=)` | 读日志尾部的唯一实现。**先过滤、再取尾**（顺序反了会让目标行落在窗口之外时整个漏掉 —— 真形状：TypeError 在第 10 行、窗口是最后 6 行） |
| 两个脚本在 `main()` **第一条语句**调 `bootstrap_logging()` | 时机见下 |
| `main.py._bootstrap_logging()` | 保留原名（`tests/test_main_entry.py` 已钉住它），改为**转发** |

判据（`tests/test_tools_logging.py`，12 例）：

| 判据 | 内容 |
|---|---|
| **派生式** | 读了日志 ⇒ 必须调 `bootstrap_logging` —— 新增脚本自动被覆盖，不用改清单 |
| **时机** | 它必须是 `main()` 的**第一条**语句。放到"要读日志了"那一步才初始化 = 前面的连接日志早丢光了，**"调用了"不等于"时机对"**（这条最容易漏） |
| **判据的底** | 只收 `ast.Call`：`import` 了但没调不算（否则"只 import 不调用"能骗过判据） |
| **不许手拼路径** | tools 下不许再出现 `"app.log"` 字面量 |
| **扫描面自检** | 扫到的 tools 文件 ≥ 20 且"读日志的脚本"非空 —— 否则循环空转、假绿 |
| **反向** | 给白名单里那个例外的脚本**加上**初始化也必须红 |

白名单只有一个：`smoke_frozen_exe.py` —— 它判的是**另一个进程**（被打包的 exe）
写的日志，自己一旦初始化，本进程的启动行就混进它要判的"新增片段"⇒ 判据假绿。
所以「它有意不初始化」这件事本身也被一条用例钉住。

反证：`tools/counterproof_logging.py` **C32**（删掉调用）/ **C33**（挪到后面）
/ **C34**（反向加上去）—— 三条都精确红 1 条。
（编号从 C28 跳到 C32：C29~C31 被另一个反证脚本 `counterproof_hygiene.py` 占着
—— 编号在 `tools/` 下必须全局唯一，否则文档里写"C29"读者不知道指哪一条。）

## 2. 日志里被刻意记下来的四件事

| # | 记什么 | 为什么必须有 |
|---|---|---|
| 1 | **环境快照**（启动时一条）：工具版本 / 运行形态（exe 还是源码）/ Python / 四个依赖版本 / 本机名 / **本机是否在域内** | 用户报"连不上"时，第一句要回答的就是"在哪台机器、哪个形态、依赖是不是齐的"。本机在不在域内直接决定网络那一环有多大可能 |
| 2 | **连接参数**：IP / 端口 / 是否 SSL / 账号**原写法** / 手填的域名与 BaseDN | 少了"原写法"就无法判断归一后的身份对不对 |
| 3 | **归一后的绑定身份**（`identity=域\用户`） | NTLM 的 salt 带域名字符串，**认错域名会被域控报成「密码错误」**。日志里没有这一行，这个陷阱在真域上永远查不出来 |
| 4 | **失败方向 + 端口可达性表** | 见下一节 —— 这是整个采集里最值钱的一条 |

## 3. 端口表怎么读（最值钱的一节）

失败时补一张 `389(LDAP)=… 636(LDAPS)=… 135(RPC-EPM)=… 445(SMB)=… 88(Kerberos)=…` 的表，
并直接给结论。三种形态的出路**完全不同**：

| 日志里看到的 | 含义 | 该做什么 | **不该做什么** |
|---|---|---|---|
| `389/636 都不通 → 先解决网络`（TIMEOUT） | 包被丢了：网段不通 / VPN 没连 / 防火墙 DROP | 检查网线/VPN/网段、确认域控在线 | ❌ 别去查账号、别去手填 BaseDN、别怀疑域策略 |
| `都被拒绝 → 服务没在听`（REFUSED） | 主机活着、那个端口没人监听 | 确认是不是填错了端口 / LDAP 服务是否在跑 | ❌ 别去查防火墙策略 |
| `至少一个 LDAP 端口通 → 优先怀疑账号` | TCP 通 ⇒ 问题在账号/域名/域策略 | 查密码、账号写法（试 `NetBIOS域\用户`）、账号是否被锁 | ❌ 别去折腾网络 |
| `由域控拒绝绑定 ⇒ 不必查网络`（不探端口） | `LDAPBindError`：**TCP 已通、请求已发出、服务器答复"不接受"** | 直接查账号写法 / 密码 / 域策略 | ❌ 别重复排查网络（这条短路省掉 1.5 秒白等） |

> **为什么这条纪律要写死**：09-14 与 09-15 各踩过一次 —— 域控网络不通时，
> 工具却提示「请手动填写 BaseDN / 该域可能禁用了匿名 RootDSE」，
> 把人引向域策略，白跑一趟。所以现在的判据是：
> **能凭异常类型判方向就不猜；判不出来就带上端口表一起给结论。**

## 4. 采集纪律（写代码时要守）

| 纪律 | 说明 |
|---|---|
| **口令一个字都不进日志** | 连长度都不记。落盘前另有 `_RedactFilter` 兜底，但那是形态匹配**不是保证** ⇒ 源头就不给 |
| **同一条文案只出现一次** | 踩过：`args=` 和 `raw=` 把同一条中文长文案写两遍，一行日志翻倍长，还容易被读成"失败了两次" |
| **标签必须准确** | `hresult=` 只给真有 `hresult` 属性的异常（`com_error`）；`OSError` 的 `args[0]` 是 `errno`，标错方向就是误导 |
| **失败不静默** | 反查失败**不致命**（可手填继续），但必须在日志里留下原因 —— 旧实现在这里一个字都没有 |
| **不碰本机身份 API** | 判断"本机是否在域内"用环境变量（`USERDNSDOMAIN`），**不许**用 `win32api.GetUserName` —— 历史上有人拿它冒充绑定身份，真域上表现为"密码错误"（有哨兵测试盯着） |

| **反证**（证明守卫不是空的） | `tools/counterproof_logging.py` —— C23~C28 + **C32~C34** 直接改源码把每个错误各犯一次，要求用例**精确变红**<br>`tools/counterproof_hygiene.py` —— C29~C31 把 09-15 那场事故**原样注入**：静态守卫红 1 条、`test_ad_client` 红 12 条、`test_diag` 红 5 条 |

**跑回归必须带 `-t .`**（否则模块按顶层名导入、量程校准不生效，白慢两分钟）：

```
python -m unittest discover -t . -s tests    # 全套
python -u tools/regression_timing.py         # 慢在哪个模块（跑完一个报一个）
python tools/counterproof_logging.py         # 反证，全部要 ✅
python tools/counterproof_hygiene.py         # 反证，全部要 ✅
python -m unittest tests.test_diag           # 光跑采集器判据
```

> ⚠️ **`discover` 中途卡住时你什么都看不到**（它只在全部跑完才输出尾巴）—— 真发生过：
> 一次回归跑了 **18 分钟没有一行输出**，只能杀掉重来。`tools/regression_timing.py`
> 逐模块起子进程、**跑完一个立刻打印一行**，并给每模块一个超时上限（超时标 `TIMEOUT`
> 而不是把整轮拖死）。
> ⚠️ 逐模块起进程比 `discover` 多 N 次解释器启动开销 ⇒ 它的"合计"**不能**当全套耗时用。
>
> **它第一次跑就抓到了真凶**：`test_ui_smoke` 一个模块 **>240s**（被超时上限截断），
> 其余 23 个模块合计只有 ~100s。顺藤摸下去是**窗口泄漏** —— 每例 `tearDown` 只调
> `close()`（**隐藏**而非销毁）⇒ 每例泄漏 13 个顶层窗口 / 396 个控件 ⇒ **越跑越慢**。
> 修好后：该模块 **≥630s → 62s**，全量 **539.8s → 112.5s**（992 例）。
> 完整诊断链与修法：`docs/回归慢的根因-界面测试窗口泄漏-2026-09-15.md`。

## 6. 用起来：出问题怎么办

1. 直接连真实域（连接 or 测试连接都行）。
2. 报错后把日志给我看，或告诉我一声 —— 日志就在
   `%APPDATA%\AD域管理工具\logs\app.log`（本机的话我可以自己读）。
3. 我按上面的对照表定位；如果是**日志没能回答的问题**，那就说明采集还有缺口，
   补采集而不是靠猜。

**GUI 之外还有一条命令行通道**（GUI 会把原因收口成一句话、`run_dev.bat` 还会吞掉 stderr）：

```
python tools/diagnose_connect.py --dc 192.0.2.10 --user corp.example.com\zhangsan --ask
```

它走**同一条生产路径**（`probe` → `test_connection` → `connect`）但每步都打完整
traceback，前面的环境自检与端口表**直接用 `diag` 那一份实现**（与写进日志的完全同源，
不会出现"脚本说的"和"日志说的"打架）。口令走 `--ask` 或 `AD_TEST_PASSWORD`，
**不进 argv、不进输出**。

⚠️ 这个脚本**自己会初始化日志**（`utils.bootstrap_logging` —— 与 GUI 同一份实现、
写同一个 `app.log`）⇒ 跑完它，日志文件里就有本次运行的完整记录。这一点是 09-15
补的：在此之前脚本的日志**一行都不落盘**，第 ⑥ 节打印的还是**上一次 GUI 运行**的
旧日志（详见 §1.6）。
